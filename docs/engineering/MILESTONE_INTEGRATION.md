# Milestone verification and independent review

JPScents applies these checkpoints inside the existing `milestone-authoring` and `milestone-workflow` skills. The locally ignored `.agents/milestones/active.md` is the active contract. The existing milestone branch and PR hold the frozen contract, evidence, reviews and corrections. ## Authoring, execution and resume

| Entry point or checkpoint                               | Who acts and what happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Explicit milestone creation or revision                 | The author reads the approved plan and canonical project rules. Name the approved acceptance criteria, relevant rule and ADR IDs, exclusions, required tests, commands and evidence for affected boundaries. Include `npm run verify` and its PostgreSQL prerequisite. Specify required D2–D4 cases when in scope and the exact focused command where appropriate. Preserve the human Manual Checkpoint and owner approval before writing `Status: Active`. Format the active file before freezing it, since the canonical formatter checks it even when locally Git-ignored. |
| **Run Active Milestone** or **Resume Active Milestone** | The orchestrator follows the existing recovery and PR path. Confirm the owner-approved contract/version, branch, base, dependencies, and remaining review budget. The implementer reads the applicable approved architecture, coding standards, ADRs, baseline and exact exceptions before editing. Escalate new rules, exceptions or material deviations through GOV-01.                                                                                                                                                                                                     |
| Implementation and handoff                              | The implementer runs useful scoped checks while editing. Run the canonical command and all required functional, integration, browser or build checks on the frozen candidate at handoff. Preliminary results may be reused only where identity and boundary match. Use the authorized milestone commit/PR path. A local dirty snapshot can support a trial or interim check. READY on an open PR requires its exact pushed commit and a clean tracked candidate.                                                                                                              |
| Independent review                                      | The orchestrator starts a separate reviewer context with the existing `independent-review` skill. Give it the frozen contract, base, target, changed-file manifest or actual diff, relevant rules/ADRs/exceptions, required evidence and previous findings. Pause implementation changes during review. Require the reviewer to inspect the diff and evidence directly and record the outcome on the same PR when authorized.                                                                                                                                                 |
| Correction and completion                               | CHANGES REQUIRED returns routine findings to the implementer. Rebind applicable checks and independently review the new snapshot. BLOCKED stops advancement until the missing capability or evidence is recovered. ESCALATE sends the owner the decision, recommended option, alternatives and consequences. Apply the existing review budget and preserve the previous findings, evidence and decisions.                                                                                                                                                                     |
| **Sync After Merge**                                    | The existing sync path verifies the human's completed merge and synchronizes the local base. It does not start implementation or review.                                                                                                                                                                                                                                                                                                                                                                                                                                      |

The author and implementer use the approved contracts as the source of truth. Independent review uses the repository protocol. The global workflow's PR transport labels `APPROVE`, `REQUEST_CHANGES` and `NEEDS_DECISION` remain compatible with repository review `PASS`, `CHANGES REQUIRED` and `ESCALATE` respectively. Preserve both the actual reviewer verdict and the workflow's historical record. An older `APPROVE` label alone provides no proof of a snapshot-bound PASS. ## Freeze the candidate and validate evidence

Record the full frozen contract version and its SHA-256, base SHA, target SHA, and the candidate digest. Use `git diff --no-ext-diff --no-textconv <base> <target>` for the committed diff and record the changed paths. For local dirty candidates, include the staged and unstaged diffs and the in-scope untracked files, separating pre-existing dependencies from milestone changes. Keep the frozen material and logs in an approved location outside the candidate. Exclude secrets and provider data. The candidate helper binds the base, HEAD, Git index, tracked working changes and non-ignored untracked file contents and modes. Record the ignored contract digest separately. Hash the frozen operative text with a consistent serialization, excluding only existing runtime metadata such as status and PR pointer. Recheck contract and candidate identity before review and before READY. A changed base, target, diff, or operative contract invalidates the affected evidence and verdict. [Verification contract](VERIFICATION_CONTRACT.md) · [Snapshot and evidence helper](../../scripts/milestone-evidence.mjs)

Run from the candidate worktree with Node 24, generated Prisma client and disposable PostgreSQL tools. Set `base_sha` to the frozen base and `evidence_dir` to an already created private directory outside the candidate. Keep all required commands and results between the two snapshots. Use the same `validate` command again before READY.

```sh
node scripts/milestone-evidence.mjs snapshot "$base_sha" > "$evidence_dir/required-before.json"
node scripts/milestone-evidence.mjs capture "$base_sha" "$evidence_dir"
# Run required milestone checks here. Capture each command, actual exit and evidence.
node scripts/milestone-evidence.mjs snapshot "$base_sha" > "$evidence_dir/required-after.json"
cmp "$evidence_dir/required-before.json" "$evidence_dir/required-after.json"
node scripts/milestone-evidence.mjs validate "$evidence_dir"
```

Capture runs `npm run verify` and creates `verify.log` and `verify.json` with the actual exit, log hash and the before/after snapshots. Use a new directory for each run. Validation checks that capture binding, then requires exactly one canonical JSON marker, quality mode, observed exit, Node version, matching HEAD and dirty flag, the complete stage list, and complete PostgreSQL counts for PASS. It checks both recorded snapshots against the current candidate. Any missing or malformed report, unknown schema, unavailable stage, incomplete counts or stale candidate is BLOCKED. A well-formed failing quality stage is CHANGES REQUIRED. Exit zero proves the canonical evidence checkpoint only. The orchestrator independently checks scope-specific artifacts and each required criterion against the same candidate, including the exercised boundary. A missing required test, browser run, integration result, or reviewer remains BLOCKED. Use trusted artifact provenance and actual exits. The digest detects identity changes and does not authenticate who supplied the output. [Enforcement matrix](ENFORCEMENT_MATRIX.md) · [Integration evidence](INTEGRATION_VERIFICATION.md)

## Completion record

Keep the following in the existing PR record, or in the isolated trial handoff when a PR is out of scope:

- Milestone ID, frozen scope and version, owner approval reference, contract digest, and acceptance checklist with evidence.
- Base, target, candidate digest, changed-file/diff identity, and required checks with commands, exits, statuses and exercised boundaries.
- Independent reviewer context ID, reviewed snapshot, verdict and artifact, correction history, outstanding risks and decisions.
- Final outcome **READY**, **CHANGES REQUIRED**, **BLOCKED** or **ESCALATE** and the next action. READY requires every approved criterion satisfied, trustworthy mandatory evidence and a separate PASS on the same candidate, with unresolved blockers cleared. Preserve the human Manual Checkpoint unchecked where applicable.

Run `npm run verify:acceptance` for release and record its aggregate exit. When an approved milestone addresses only some acceptance cases, require passing evidence for the exact in-scope cases and preserve the grouped command's actual FAIL and outstanding cases when it is run. The aggregate command is required to pass when the contract requires the full suite.

Only the owner authorizes material architecture changes, exceptions, destructive operations, merge, hosted protection or deployment. A scoped READY can coexist with a failed release decision. D2–D4 acceptance remains **FAIL**, and promotion stays blocked until the exact release candidate satisfies the full contract. Never treat a passing PR quality job as release authority. [Release decision](VERIFICATION_CONTRACT.md#release-decision)
