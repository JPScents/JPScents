## Run the suites

Use Node 24, the installed project dependencies and generated Prisma client, and PostgreSQL executables `initdb`, `pg_ctl`, and `psql` on `PATH`. The test run used Node 24.14.1, Vitest 4.1.11 and PostgreSQL 14.17. Run from the repository root as a non-root user on a Unix host that permits PostgreSQL shared memory. If the generated client is missing, follow the [README's isolated verification instructions](../../README.md#agent-verification-without-secret-file-access) to generate it in a copy that excludes secret files. The suite needs neither a Supabase project nor provider credentials.

```sh
env -i PATH="$PATH" CI=1 npm run test:integration -- --no-cache --configLoader runner
env -i PATH="$PATH" CI=1 npm run test:integration:acceptance -- --no-cache --configLoader runner
```

The first command selects the current-invariant group and should exit 0. The second selects the approved-design group and exits 1 while D2–D4 remain pending. Each command reports the other group as filtered out. The default unit command excludes the integration directory. A setup error fails the suite before any selected case runs. A test assertion or repository error after setup is reported against its scenario. [Integration config](../../vitest.integration.config.ts) · [Default config](../../vitest.config.ts) · [Package scripts](../../package.json)

### Isolation and realism

- Each run creates an owner-only `/tmp/jpit.*` directory and an empty PostgreSQL cluster listening on a private Unix socket. The runner rejects inherited `DATABASE_URL`, `DIRECT_URL`, and `APP_ENV_FILE` by name before creating the directory. The test config disables Vite environment-file loading. The harness checks socket-only access before applying SQL and constructs the app and observer connection URLs from the temporary directory.
- The SQL fixture supplies the minimum `anon`, `authenticated`, `auth.jwt()`, and Storage table and function definitions needed by the five committed migrations. The harness applies each unmodified `migration.sql` in order with `psql` and stops on any SQL error. The resulting tables, constraints, triggers, transaction isolation, grants, and RLS policies execute in PostgreSQL. This verifies the migration SQL on an empty cluster. Prisma's deployment tooling and upgrades of populated databases were outside the run.
- Tests use the application repositories and real Prisma PostgreSQL adapter. A separate client inserts synthetic, uniquely keyed fixtures and inspects committed state. The lock test uses a separate connection to hold the row lock and observes the application session waiting in `pg_stat_activity` before allowing the competing write to commit. The replay and cancellation checks use sequential calls. The application pool has one connection per process.
- The runner disconnects both clients, stops its own cluster, and removes its own directory. The setup failure path also cleans up. A forced kill can prevent teardown. For a confirmed leftover test cluster, stop it with `pg_ctl -D /tmp/jpit.<confirmed-directory>/data -m fast -w stop` before removing that specific directory. Never point this suite or its cleanup at a configured or shared database.
