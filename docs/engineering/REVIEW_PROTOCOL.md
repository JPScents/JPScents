# Independent architectural review

Independent review evaluates a frozen implementation against its accepted scope, approved contracts, and actual verification evidence. The review verdict covers that candidate. Merge, release and deployment decisions retain their existing approval requirements. [Architecture verification rules](../architecture/ARCHITECTURE.md#4-verification-and-exceptions) · [ADR-0004](../architecture/adr/0004-merge-and-release-verification.md) · [Quality gates](QUALITY_GATES.md)

## Request and isolate the review

The orchestrator MUST select a separate agent context with no implementation role on the candidate. Supply the handoff below and omit the implementer's deliberation. Prior findings and implementation claims may be supplied as context for verification. A reviewer MUST NOT approve their own changes. If a separate context or the candidate is unavailable, report **BLOCKED** and identify the prerequisite.

| Handoff input           | Minimum content                                                                                                                                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository and revision | Working directory and repository identity, exact base and candidate SHA, and PR or review artifact location when applicable. For uncommitted work, identify the base and provide a frozen diff with a digest and any in-scope untracked files. |
| Proposed change         | Complete inspectable diff, intended behavior, feature or frozen milestone contract and version, acceptance criteria, exclusions, and affected entry points.                                                                                    |
| Applicable contracts    | Relevant rule IDs, accepted ADRs, scoped exception approvals, baseline findings and previous review IDs. Give the reviewer access to the canonical documents.                                                                                  |
| Evidence                | Actual commands, exit codes and logs or artifacts, tested revision or snapshot, runtime and isolation details, boundary exercised, and known limitations. Identify the checks the reviewer may run safely.                                     |

The reviewer MUST verify the base, candidate and diff independently. Inspect the affected source, callers, dependencies and tests at that revision. With an uncommitted snapshot, read the patch and its base, and resolve affected files against the frozen snapshot. Pause candidate changes during review or use an immutable checkout. If candidate identity or coverage changes, stop and obtain a new handoff. Record the exact reviewed revision or snapshot in the verdict. A corrected candidate needs another independent pass, with dispositions for the earlier findings.

## Review the affected boundaries

Read applicable repository instructions, the approved architecture and coding standards, and the relevant accepted ADRs. Trace the normal entry point through the changed behavior. Start with the failure modes that could affect customers, security or persisted data. Follow unchanged callers and dependencies where they can change the outcome. [Repository instructions](../../AGENTS.md) · [Architecture](../architecture/ARCHITECTURE.md) · [Coding standards](CODING_STANDARDS.md) · [Accepted ADRs](../architecture/adr/README.md)

| Area                               | Review questions                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ownership and dependency direction | Do routes, actions, services, repositories and UI modules own their approved responsibilities? Are feature calls through supported public APIs, with business rules in the owning feature? Does each new abstraction serve an actual responsibility?                                                                                     |
| Correctness and persistence        | Does each acceptance criterion hold across normal, failure and edge paths? Inspect authorization before effects, validation, authoritative state, transaction ownership, atomicity, ordering, retries, idempotency, race conditions, stale writes and legal state transitions. Check side effects and regressions in connected features. |
| Types and maintainability          | Inspect data contracts, unsafe narrowing, error handling, security and privacy boundaries, naming, duplication, and complexity. Apply the review thresholds and scoped exceptions from the approved standards. Judge legitimate implementations by their contracts and effects.                                                          |
| Tests and evidence                 | Check that assertions observe outcomes and consequential side effects. Review boundary mocks, concurrency and negative cases. Compare the tests with the actual path and identify production behavior a mock cannot establish.                                                                                                           |

## Verify architectural approval before verdict

The reviewer MUST apply the [mandatory approval contract](CHANGE_CONTROL.md#mandatory-architecture-approval-contract). Require a task/change-to-ADR mapping with classifications, exact Accepted ADR/version, owner approval reference/scope/conditions and propagation/acknowledgement evidence. Independently inspect the diff for decisions omitted from that mapping. Verify the actual owner decision; a status string, general plan approval, green checks or an implementer's assertion is insufficient.

Record each architecture change as covered, decision required or approval evidence unavailable. A required new decision is ESCALATE and affected tasks are BLOCKED; unavailable evidence is BLOCKED. Either prevents PASS, APPROVE, READY and READY FOR MERGE for the affected candidate. Unchanged independent tasks can retain their scoped results but cannot make the blocked milestone ready. If code preceded its approval, record the violation and stop further affected work; do not legitimise it retroactively. The owner decides scope/adoption, and the resulting candidate still needs verification and review.

The review artifact MUST include: change/task, relevant rule, ADR/version/status, direct owner evidence, scope match, propagation consistency and unresolved decision. Use None with rationale when no architectural change exists. The reviewer MUST NOT accept an ADR or substitute review/merge approval for the pre-implementation architecture decision.

## Verify the evidence

The reviewer MUST check what ran, on which candidate, with what exit status and at which boundary. Inspect the relevant deterministic results under the [verification contract](VERIFICATION_CONTRACT.md#status-and-evidence) and [enforcement matrix](ENFORCEMENT_MATRIX.md). Treat old output, an implementation summary, a different SHA, or an unmatched dirty worktree as insufficient for current required evidence. Read the tests as well as the command output.

Reuse trustworthy evidence matched to the candidate. Run focused authorized checks when evidence is missing, stale or ambiguous and the prerequisite is safely available. Avoid repeating expensive checks with equivalent valid evidence. Database tests against migrated disposable PostgreSQL, browser runs and provider integrations each establish their observed boundary. Mocked tests only establish behavior inside their test boundary. Preserve unavailable build, browser, provider, security or release evidence as unverified. Report a required evidence gap as **BLOCKED** when it prevents a decision. [Integration evidence and gaps](INTEGRATION_VERIFICATION.md) · [Release decision](VERIFICATION_CONTRACT.md#release-decision)

## Record findings

Every material finding MUST have a stable ID such as `REV-001`, a severity and a certainty, an origin, repository-relative evidence, an affected rule or acceptance criterion, impact and a focused corrective action. Cite the revision side and line or symbol. For a missing check, cite the affected path or criterion and identify the missing artifact. Keep IDs across review passes and explicitly resolve, retain or supersede each earlier finding.

| Severity | Use when                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Critical | The change can cause severe unauthorized access, destructive or irreversible data loss, or systemic failure requiring immediate containment. |
| High     | An authorization or consistency failure, core workflow regression or required verification gap exposes users or data to significant harm.    |
| Medium   | A bounded functional regression, missing regression protection or material maintainability issue has limited impact.                         |
| Low      | A localized defect has limited consequence and low correction cost.                                                                          |

- **Certainty** — **Confirmed** when direct source or executed evidence establishes the finding. **Probable** when evidence supports a causal path with a material assumption still open. **Unverified** when available evidence cannot establish the behavior or check. Identify the evidence that would resolve uncertainty.
- **Origin** — Compare base and candidate before recording a defect as introduced. Distinguish **introduced**, **worsened baseline**, **existing debt**, **approved change pending**, **approved exception** and **unverified risk**. Cite the [baseline finding](COMPLIANCE_BASELINE.md#findings-register), [exception approval](EXCEPTIONS.md#approved-exceptions) or accepted decision where applicable. Verify their scope and current status against the source and newer evidence. Record legitimate variations as reviewed context when useful.
- **Blocking effect** — A finding blocks if it breaks an acceptance criterion or mandatory rule applicable to the change, or leaves a required high-risk outcome unresolved. Assess effect separately from severity. Unchanged debt and pending decisions stay visible. They become relevant blockers when the change worsens them, promises to address them, or depends on their completion for required acceptance or release evidence.

## Decide and escalate

| Outcome              | Required basis                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PASS**             | Applicable acceptance criteria are satisfied, required evidence is available and passing, and no blocking findings remain. Automated success alone is insufficient.                                     |
| **CHANGES REQUIRED** | A confirmed blocking defect or failure under the accepted scope requires a routine correction and a new independent review.                                                                             |
| **BLOCKED**          | A required artifact, environment, separate reviewer or existing approval record is unavailable, or material uncertainty cannot be resolved with available evidence. Identify the specific prerequisite. |
| **ESCALATE**         | Proceeding requires an explicit human decision about scope, architecture, an exception or another consequential action.                                                                                 |

If a human decision governs how the work can proceed, use **ESCALATE**. Otherwise report confirmed blockers as **CHANGES REQUIRED** and list any outstanding evidence alongside them. When required evidence is the remaining obstacle, use **BLOCKED**. Resolve ordinary corrections with the implementer.

Escalate a proposed change to an approved contract, a new exception or suppression, conflicting product requirements, a material security, privacy or integrity decision, a consequential trade-off without precedent, destructive or irreversible operations, or a merge, release or deployment decision requiring owner authority. State the problem, affected requirement and evidence, recommended option, viable alternatives and consequences, and the exact decision requested. Apply [GOV-01](../architecture/ARCHITECTURE.md#4-verification-and-exceptions) for exceptions. Record approval through its existing canonical process.

The reviewer MAY inspect code, specs, diffs, tests and evidence, run authorized checks, request corrections, recommend decisions, and issue a verdict. The reviewer MUST NOT implement fixes, approve architectural changes or exceptions, modify approved standards, weaken verification, merge, deploy or represent a missing independent review as completed. Posting a review to a PR requires separate authorization under the applicable workflow.

## Review artifact and handback

Keep the detailed review in the authorized repository review artifact or PR record. When neither is writable, return the complete review to the orchestrator with the recording limitation. The owner receives the verdict, blocking IDs, candidate revision and any decision requested.

```text
Outcome: PASS | CHANGES REQUIRED | BLOCKED | ESCALATE
Repository / base / candidate or frozen snapshot / contract version / pass:
Acceptance: criterion | PASS / FAIL / NOT VERIFIED | evidence
Blocking findings: ID | severity | certainty | origin | path:line or symbol
  Requirement | impact | corrective action
Non-blocking recommendations: same finding fields, or None
Evidence examined: source, checks and results, revision and exercised boundary
Required corrections or approvals: action, prior finding disposition, or None
Remaining uncertainty: missing evidence, affected decisions, or None
```

Invoke the [repository-local skill](../../.agents/skills/independent-review/SKILL.md) explicitly in the separate reviewer context. The existing milestone workflow retains its independent review, PR record, verdict vocabulary, review budget and human merge step. The milestone checkpoints integrate this protocol with authoring, execution and resume.
