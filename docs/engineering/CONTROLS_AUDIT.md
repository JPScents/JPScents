# Engineering Controls and Enforcement Audit

- **Audit date** — 12 November 2026
- **Inspected commit** — `cda1783b792fa392ff0f0563d948d9eaa6e07837` on local `main`
- **Scope** — Current checkout, installed toolchain, and read-only GitHub and Vercel metadata where accessible. The [codebase intelligence report](../CODEBASE_INTELLIGENCE.md) was context. Findings below were checked independently. This audit records existing controls and decisions for Task 4.

## A. Executive summary

JPScents has a working local quality gate and a useful custom architecture checker. Architecture, formatting, lint, strict type checking, and all **135 tests across 26 files** passed. The checker reliably rejects covered naming, import, and Prisma boundary violations when invoked. It also accepted a temporary fixture with a dependency cycle and incorrectly placed logic, confirming that semantic responsibility still depends on review. A passing order test logged a `TypeError` without detecting a failed success path.

The central gap is **when checks run and what their results prove**. No active commit or push hook was found, and no tracked CI workflow invokes the local checks. The documented Vercel build command runs Prisma generation and Next.js compilation. It has no invocation of the full quality gate. Hosted requirements remain unverified. In an isolated copy, Prisma validation and generation succeeded, then Next.js compilation stopped at Google Fonts DNS resolution. Rollback, concurrent writes, database policies, and browser-to-backend flows remain unverified in this audit.

## C. Architectural consistency findings

- **Cart and checkout composition follows the ownership rule.** The perfume-detail hook combines catalogue variants and Cart at the route. The checkout wrapper bridges Cart state into Orders. Cart's action uses Catalogue's server entry for published variants. Cart's single public `index.ts` forwards individually marked client modules. That is consistent with optional runtime entry points for a feature with no privileged public reads. [Purchase hook](../../src/app/%28public%29/perfumes/%5Bslug%5D/_hooks/useVariantPurchaseControls.ts#L5) · [Checkout wrapper](../../src/app/%28public%29/checkout/_components/Checkout.tsx#L3) · [Cart action](../../src/features/cart/actions/resolve-cart.action.ts#L3) · [Cart exports](../../src/features/cart/index.ts#L1)
- **Orders and Customers demonstrate the intended transaction boundary.** `submitOrder` owns the cookie effect. `createOrder` parses input, invokes one atomic operation, then resolves images and maps the response after the transaction. The order repository passes its transaction to `resolveCustomerForOrder` through Customers' server entry. Customers owns identity resolution. A repository-owned operation exposed for that purpose is an explicit exception to internal repository isolation. [Action](../../src/features/orders/actions/submit-order.action.ts#L6) · [Service](../../src/features/orders/services/order.service.ts#L91) · [Transaction](../../src/features/orders/repositories/order.repository.ts#L89) · [Customer entry](../../src/features/customers/server.ts#L3) · [Allowed transaction participation](../../.agents/skills/feature-structure/SKILL.md#L60)
- **Admin catalogue demonstrates when a service earns its place.** `savePerfume` authorises, parses, and handles redirect/revalidation. `savePerfumeWithImage` coordinates upload and cleanup around the atomic repository write. Simpler guarded mutations call their repository directly. Both patterns match the action rules. Catalogue's public server entry also re-exports published-only reads, while protected Admin reads go through guarded service functions. [Save action](../../src/features/catalogue/actions/save-perfume.admin.action.ts#L28) · [Image orchestration](../../src/features/catalogue/services/save-perfume.service.ts#L8) · [Direct variant write](../../src/features/catalogue/actions/save-variant.admin.action.ts#L11) · [Catalogue entry](../../src/features/catalogue/server.ts#L5) · [Admin reads](../../src/features/catalogue/services/admin-catalogue.service.ts#L17)

The action delegates the raw input. The skill assigns runtime input handling to actions and ordinary repository inputs/results to the orchestration layer. Validation is present and precedes database work. This is a responsibility-placement discrepancy to resolve, with no missing validation inferred. [Action rule](../../.agents/skills/feature-structure/SKILL.md#L72) · [Service and parser call](../../src/features/orders/services/order.service.ts#L91)
- **Tooling exceptions are intentional but broad in the checker.** The shared Prisma module owns lazy client lifecycle and the seed entry owns its standalone lifecycle. The seed calls a seed-only repository. The checker exempts those two files from its Prisma syntax restrictions and also exempts files under a `repositories` path from that scan. Inspection confirmed the representative lifecycle modules match their stated roles. The exemptions themselves cannot prove that. ## F. Decisions for Task 4

1. **Choose where a check becomes mandatory.** Establish which existing checks should block a merge, which evidence is required before deployment, and who owns each result. Inspect actual GitHub and Vercel settings before deciding where enforcement belongs.
2. **Set the limit of mechanical architecture enforcement.** Decide which dependency rules justify deterministic checks, including whether cycles through public APIs must be blocked. Decide which rules require review of representative flows, such as responsibility placement, authorization, mapper purity, and transaction-client use. Resolve where Orders' request decoding belongs before encoding a blanket rule.
3. **Set evidence by failure mode.** Decide which order and inventory changes require a disposable migrated-database run and which Auth, Storage, or UI changes need preview or browser evidence. Require successful outcome assertions for success paths such as returning-customer checkout. Define what a blocked build or unavailable environment means for release readiness.
4. **Choose the source of authority for agents.** Decide which guidance is canonical, which files delegate to it, and how archived product decisions, default commit behaviour, and milestone-only approvals are presented to avoid ambiguity.
5. **Assign ownership for security checks and clean verification.** Confirm existing hosted scanning before selecting any repo-level coverage. Decide who checks advisories and secret exposure, how a clean checkout generates the Prisma client, and what build network access the release path expects.
