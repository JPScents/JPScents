## Incremental enforcement strategy

- Use this revision and finding IDs as the comparison point. Match debt by rule, path and symbol, then assess the changed behaviour. A new occurrence elsewhere or an expanded affected scope is a new deviation, even when it shares a rule with existing debt.
- Keep running the full existing quality check for changes subject to the approved gate. Review new and materially changed code against the approved rules. Record open baseline findings relevant to a change, and keep unrelated findings visible for their owning work. Baseline debt carries no exception approval.
- Use the approved complexity measures to trigger review and record the outcome. Preserve cohesive transactions and interaction lifecycles. Check the actual changed functions and their responsibility before deciding whether to extract anything.
- Where a later enforcement change is approved, add coverage within the existing checker, ESLint, or test path where practical. Verify a compliant case and a violation, and document the mechanical limits. Keep semantic and integration obligations in review and evidence. D5's hosted wiring is still an implementation decision. [Approved verification](../architecture/ARCHITECTURE.md#4-verification-and-exceptions) · [Standards enforcement matrix](CODING_STANDARDS.md#standards-to-enforcement-matrix)
- Close a finding with evidence that covers its original boundary. Record the verified revision, affected tests, and any remaining limitations. Any deviation requires explicit, scoped approval under GOV-01 and STD-025. [Exception lifecycle](EXCEPTIONS.md#recording-review-and-supersession)
