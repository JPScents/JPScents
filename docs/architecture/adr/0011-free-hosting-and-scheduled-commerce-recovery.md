## Context

The existing Vercel team is on Hobby. Hobby is restricted to personal, non-commercial use. An external scheduler would address the timer only. The store needs a commercial-use hosting tier with a hard $0 limit, support for the full Next.js App Router application and automatic deploys from `main` after the required GitHub check and human merge. JPScents/JPScents is already public, so it qualifies for Netlify Free's Git integration. A disposable build of `36bf6ee3e0d6b07e5c3adb99dfe762253f9526d4` using Netlify CLI 27.17.0 and its OpenNext adapter 5.16.6 packaged both the Next.js server and the Node session proxy successfully. The build used no hosted credentials and published no site. ## Decision and trade-offs

Use **Netlify Free** for the existing Next.js app and its isolated Deploy Preview. Retain Supabase Postgres, Auth and Storage. Use **Supabase Cron with pg_net** in each authorised project to check for due commerce work each minute. Call that project’s existing authenticated reconciliation route when work is due and once per hour when idle so Admin Operations still shows an application heartbeat. Store the target and its deployment-scoped bearer in the corresponding Supabase Vault and inject the matching bearer at runtime on Netlify. Use the already durable job leases, recovery and Admin visibility. Confirm outbound HTTP responses and completed app runs, since a successful `pg_cron` row only establishes that a request was queued. Keep the Preview schedule scoped to PR #3 and disable it when verification finishes. Keep operational run history bounded on the Free database. Verify that the due-work query covers the same reservation, attempt, receipt, refund and email eligibility and expiring claims as the app, and allows the existing handler to remain authoritative for state changes. [Supabase Cron](https://supabase.com/docs/guides/cron) · [Supabase pg_net](https://supabase.com/docs/guides/database/extensions/pg_net) · [Supabase Vault](https://supabase.com/docs/guides/database/vault)

- Keep `JPScents quality` as the required check with unit, integration and Chromium E2E. Git deploys trusted branch previews and deploys `main` automatically after the human merges. The GitHub source and required check remain the release gate. Keep untrusted fork builds away from credentials. Configure a server-only deployment mode per environment so Preview can only use test Paystack credentials and Production can only use live credentials. Preserve separate database, provider, origin, webhook and schedule settings. Keep secrets out of source, SQL literals, build logs and preview artifacts.
- Netlify Free has a hard limit of 300 shared credits a month and pauses service when exhausted. An unconditional 31-day minute schedule could add 44,640 HTTP calls. At published rates that is about 9 request credits and about 124 compute credits if the function averages one billed second with 1 GB memory, before real traffic, bandwidth and 15 credits per published production deploy. At two seconds it could use about 257 total credits. The minute-level database check avoids invoking the host when it has no work, while the hourly idle heartbeat accounts for up to 744 HTTP calls a month. Measure idle and active runs in the isolated Preview, include traffic and deploys in the budget, and recheck before domain cutover. Keep a single Next.js app and the current handler. [Credit rates](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/) · [Function memory and billing](https://docs.netlify.com/build/functions/usage-and-billing/) · [Free plan pause behavior](https://docs.netlify.com/manage/accounts-and-billing/billing/resume-paused-projects/)
- Prove Admin sign-in and session refresh, catalogue images, hosted image upload, guest checkout, the Paystack callback and signed webhook, refund recovery, Resend, and scheduled work against the exact isolated deployment. Confirm the documented Netlify binary payload limit against the Admin's current 5 MiB image allowance. If it is incompatible, bring back the smallest evidence-based fix with its impact before cutover. Keep Google Places optional in live checkout. Default to manual address entry unless the owner enables Places with an enforced quota within the no-cost allowance. Keep the hosted Places acceptance scenario until its required evidence is provided or the owner explicitly revises it. Paystack transaction fees on real payments are separate from hosting. [Netlify function limits](https://docs.netlify.com/build/functions/configuration/) · [Google Places billing](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing) · [Paystack pricing](https://paystack.com/pricing)
- Native Netlify Scheduled Functions run on published deploys and add a function invocation. Supabase Cron can exercise the same protected endpoint on both isolated Preview and Production. GitHub Actions scheduling has a five-minute minimum. Cloudflare Workers Free has a 10 ms CPU limit per request, and Cloudflare says SSR apps usually need its paid tier. OCI Always Free supports ordinary Node hosting but can reclaim idle instances and requires VM maintenance. The smallest managed test is Netlify plus the existing Supabase projects. [Netlify schedule limits](https://docs.netlify.com/build/functions/scheduled-functions/#limitations) · [GitHub minimum interval](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule) · [Cloudflare SSR guidance](https://developers.cloudflare.com/workers/static-assets/migration-guides/vercel-to-workers/) · [OCI Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

## Scope, rollout and verification

Milestone 7 stages E–F, AC-02 and AC-10–12, T-04, T-06–07 and CU-07–08. Apply ARC-05/08/10/11, INV-03–05/07, VER-01–03 and STD-015/016/019–025. Preserve Stage C–E data and recovery semantics. Align the deployment mode, setup, operations and milestone records after approval. Before cutover, record automatic build source, host behavior and quota use, signed provider test, denial of invalid scheduler credentials, real scheduled recovery within the proposed cadence, idle skips and heartbeat, release of expired claims, and a recovery build that preserves in-flight work. Keep the existing domain serving until the new host is proven. During authorised cutover use one active schedule and webhook target per environment, preserve the database and domain, and verify an automatic release and the rollback path with new payment initiation paused. Normal future deploys follow the reviewed merge automatically.
